## 场景与成果

供应商订单、客服记录和业务表单往往没有统一格式。批处理系统既要理解差异，又要让每条数据的成功、失败和重试都有明确落点。

通过 Managed Session 编排多格式数据的读取、解析、计算、校验和回写，形成可回看的批处理任务。

本文根据Qoder Agents 团队提供的 showcase 资料整理。流程图与分工表用于解释案例中的方法；后面的具体示例是复用建议，不作为生产运行的实测结论。

## 实现思路

### 一次任务如何流经产品

原材料覆盖非实时、格式易变的数据任务。Agent 处理输入差异，执行环境完成实际计算，Skill 承载可复用的业务规则。

```mermaid
flowchart LR
  N0["建立任务清单"] --> N1
  N1["隔离解析"] --> N2
  N2["逐条校验"] --> N3
  N3["幂等回写"]
```

每个环节都需要把自己的输入与结果交给下一步。后续步骤据此继续工作，用户也能沿着这条链查看结果从哪里产生、在哪一步需要确认。

### 角色分工与权威事实

| 组成部分 | 在案例中的职责 |
|---|---|
| 任务编排 | 批次、记录标识与检查点 |
| Agent | 识别格式并应用业务规则 |
| 结果存储 | 校验、幂等回写与失败队列 |

批量大小影响吞吐、失败重试成本和定位难度。先按可独立校验的记录划分任务，再调并发；不要把整批成功与否绑定到一个长会话的最终回答。

### 沿着一个具体任务展开

把三种供应商格式的合成订单统一成标准记录。输入格式会变化，但订单号、币种、金额和日期的输出契约固定。

1. **建立任务清单**：为输入文件或记录分配稳定标识与内容摘要，记录批次、来源和待处理状态。
2. **隔离解析**：按文件或小批次创建执行单元，先识别格式，再由业务规则提取标准字段。
3. **逐条校验**：检查必填字段、金额类型和日期格式；不合格记录进入失败队列，保留原输入引用。
4. **幂等回写**：使用记录键与版本写入结果，保存检查点；重跑只处理未完成或失败的输入。

这条流程的交付物需要保留过程中使用的依据。某一步缺少数据或执行失败时，应让状态继续可见，避免后续环节把它当作已经完成的结果。

### 让结果可以被核对

下面用一组合成数据说明预期交付。它是应用侧的说明样例，不是 QCA API 请求，也不是生产记录。

```json
{
  "input": {
    "records": [
      {
        "id": "a",
        "amount": "12.50"
      },
      {
        "id": "b",
        "amount": "unknown"
      }
    ]
  },
  "expected": {
    "accepted": [
      {
        "id": "a",
        "amount": 12.5
      }
    ],
    "rejected": [
      {
        "id": "b",
        "reason": "invalid amount"
      }
    ]
  }
}
```

成功和失败记录都必须可定位。再次处理同一输入时，成功记录不新增副本，失败记录仍能被单独重试。

## 复用建议

落地时可以先复现上面的一个任务，用已知输入核对交付结果，再补齐下面这些失败或歧义场景。通过后再扩大任务范围。

| 失败或歧义场景 | 需要保留的行为 |
|---|---|
| 某条记录无法解析 | 其他记录继续，失败项携带原因。 |
| 回写后进程中断 | 恢复后不产生第二份结果。 |
| 输入文件更新 | 生成新版本，旧结果仍可追溯。 |
