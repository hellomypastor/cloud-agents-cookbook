## 场景与成果

一笔“充电费用不对”的投诉，可能同时涉及订单时长、设备状态、分时费率、服务费和优惠。传统排查容易按团队串行传递问题：订单团队提供明细，设备团队核对日志，计费团队重算金额，最后再由客服解释。

霄羽的原 showcase 采用主诊断 Agent 加多个专业 Agent 的方式，分别处理订单、设备、计费和趋势，再汇总证据。现有素材能确认这个分工和演示入口，不能证明生产诊断准确率或分钟级效果。下面保留历史界面，说明原资料中可以确认的专业分工。

## 实现思路

### 主 Agent 首先要统一问题范围

开始并行分析前，要明确同一订单、同一设备和同一时间范围。否则计费 Agent 可能看本次订单，设备 Agent 看全天告警，趋势 Agent 看一周均值，三个看似合理的结论却无法直接合并。

可先把用户的话整理成一份调查摘要：用户认为哪项异常、订单标识是什么、预期与实际差多少、哪些材料已经获得。标识缺失时先补齐；不能把“费用高”自动等同于“计费错误”。

### 并行的是取证，汇总的是可比较事实

下面的分工来自原 showcase 的专业角色；证据字段和汇总契约是本文的参考设计。

| 专业任务 | 需要读取 | 输出事实 | 不能单独决定 |
|---|---|---|---|
| 订单核对 | 起止时间、金额、状态、优惠 | 本次交易发生了什么 | 设备是否故障 |
| 设备核对 | 对应时段日志、状态与中断记录 | 是否观察到相关异常 | 异常是否导致全部差额 |
| 计费复算 | 分时费率、服务费和取整规则 | 可复算金额及差异 | 缺失收费项的真实值 |
| 趋势对比 | 可比设备和时段的数据 | 是否偏离同类基线 | 相关性是否构成根因 |

专业 Agent 的结果应携带数据时间窗、来源和缺失项。主 Agent 不能用“多数角色都认为有问题”代替证据：四个角色可能引用了同一条错误输入，投票不会增加独立信息。

### 专业结果冲突时如何收尾

如果订单时间与设备日志时区不一致，先对齐时间再判断关联。如果计费复算和账单不一致，先核查收费分项和版本。如果趋势 Agent 发现类似订单普遍偏高，也只能增加排查优先级，不能覆盖单笔订单的原始证据。

推荐为每个结论保留“观察、推断、未决”三种身份。后续补充数据时，主 Agent 更新对应条目，避免把第一轮猜测固化成工单结论。

## 复用建议

先用一笔有人工答案的历史测试订单验证完整链路，再依次移除服务费、设备日志或费率版本，观察报告是否正确降级。验收重点包括复算是否一致、缺口是否明确、专业结果是否引用同一调查范围，以及客服能否据此完成下一步。

性能测试应把并行取证和等待外部系统的时间分开。若瓶颈在数据接口，增加 Agent 数量未必更快。原 showcase 的效率描述可以作为待验证目标，不能直接当作当前系统已经达到的指标。
