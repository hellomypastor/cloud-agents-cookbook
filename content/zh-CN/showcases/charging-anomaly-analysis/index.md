## 场景与成果

一笔异常充电订单可能同时涉及设备事件、订单状态和费率规则。只查看某一个系统，容易把数据缺口误判成故障原因。

围绕充电异常，将订单、设备、计费和趋势分析拆成专业任务，汇聚证据形成诊断说明。

本文根据霄羽提供的 showcase 资料整理。流程图与分工表用于解释案例中的方法；后面的具体示例是复用建议，不作为生产运行的实测结论。

## 实现思路

### 一次任务如何流经产品

原案例采用主诊断角色协调不同分析视角。各角色需要使用一致的时间窗口、设备标识与事件口径，汇总时区分观察事实和待验证假设。

```mermaid
flowchart LR
  N0["建立范围"] --> N1
  N1["独立分析"] --> N2
  N2["对齐证据"] --> N3
  N3["输出解释"]
```

每个环节都需要把自己的输入与结果交给下一步。后续步骤据此继续工作，用户也能沿着这条链查看结果从哪里产生、在哪一步需要确认。

### 角色分工与权威事实

| 组成部分 | 在案例中的职责 |
|---|---|
| 主诊断角色 | 统一事件范围并汇聚结论 |
| 专项角色 | 订单、设备、计费与趋势分析 |
| 数据工具 | 返回原始记录和时间线 |

订单、设备和计费系统可能存在时间偏差。先对齐时区和业务标识，再做并行分析；否则多个专业结论只是把同一份不一致重复描述。

### 沿着一个具体任务展开

使用合成充电订单复现“订单金额高于预期”，同时检查设备事件、充电时长、费率版本和订单状态。

1. **建立范围**：固定订单号、站点、时间窗口与用户问题，不把其他站点的数据混入本次诊断。
2. **独立分析**：订单角色检查状态，设备角色检查事件，计费角色核对费率与时长，趋势角色提供同期背景。
3. **对齐证据**：用统一时间线汇聚结果，指出费率切换或事件缺失发生在何时。
4. **输出解释**：返回金额复算、异常依据和待核查项，不把退款或账单修改隐含在诊断中。

这条流程的交付物需要保留过程中使用的依据。某一步缺少数据或执行失败时，应让状态继续可见，避免后续环节把它当作已经完成的结果。

### 让结果可以被核对

下面用一组合成数据说明预期交付。它是应用侧的说明样例，不是 QCA API 请求，也不是生产记录。

```json
{
  "input": {
    "segments": [
      {
        "hours": 1,
        "rate": 2
      },
      {
        "hours": 0.5,
        "rate": 4
      }
    ],
    "billed": 5
  },
  "expected": {
    "calculated": 4,
    "difference": 1,
    "cause": "requires investigation"
  }
}
```

复算可证明账单与本例费率之间存在差额，却不能直接判定是设备故障或计费系统错误；还需要核查服务费等口径。

## 复用建议

落地时可以先复现上面的一个任务，用已知输入核对交付结果，再补齐下面这些失败或歧义场景。通过后再扩大任务范围。

| 失败或歧义场景 | 需要保留的行为 |
|---|---|
| 费率在订单中途变更 | 分段计算并展示使用的版本。 |
| 设备事件缺失 | 标记数据缺口，不推断已发生的故障。 |
| 趋势统计与单笔证据不一致 | 优先说明单笔证据及样本限制。 |
