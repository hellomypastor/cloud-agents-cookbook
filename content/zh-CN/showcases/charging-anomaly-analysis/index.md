围绕充电异常，将订单、设备、计费和趋势分析拆成专业任务，汇聚证据形成诊断说明。

本篇根据 showcase 资料整理，原案例贡献者：霄羽。内容介绍材料中的方案，不将其等同于已验证的生产部署或量化收益。

## 实现思路

原案例采用主诊断角色协调不同分析视角。各角色需要使用一致的时间窗口、设备标识与事件口径，汇总时区分观察事实和待验证假设。

### 实践演练：从任务到验收

使用合成充电订单复现“订单金额高于预期”，同时检查设备事件、充电时长、费率版本和订单状态。

以下是可复用的实现与验收建议，不代表演示站已公开这些后端能力，也不表示这些检查已经执行通过。演练使用合成或获授权输入；JSON 是应用侧记录示意，不是 QCA API 请求。

### 分步实现与交付物

#### 1. 建立范围

固定订单号、站点、时间窗口与用户问题，不把其他站点的数据混入本次诊断。

#### 2. 独立分析

订单角色检查状态，设备角色检查事件，计费角色核对费率与时长，趋势角色提供同期背景。

#### 3. 对齐证据

用统一时间线汇聚结果，指出费率切换或事件缺失发生在何时。

#### 4. 输出解释

返回金额复算、异常依据和待核查项，不把退款或账单修改隐含在诊断中。

### 输入输出记录示例

```json
{
  "order_id": "synthetic-order-01",
  "tariff_version": "test-tariff-v2",
  "analysis_only": true,
  "evidence_sources": [
    "order",
    "device-events",
    "tariff"
  ]
}
```

将这份记录与产物或报告一起保存，用来回答“这份结果来自哪个输入、哪个版本”。凭证不写入记录。输入变化后应重新判断旧结果是否适用，不能静默复用。

## 复用建议
用合成订单和设备事件复现一类异常，要求每个结论引用对应证据。原在线地址内容已变更，本页以案例说明保留，不再链接旧站。

### 关键取舍

订单、设备和计费系统可能存在时间偏差。先对齐时区和业务标识，再做并行分析；否则多个专业结论只是把同一份不一致重复描述。

### 故障与验收检查

| 检查条件 | 预期结果 |
|---|---|
| 费率在订单中途变更 | 分段计算并展示使用的版本。 |
| 设备事件缺失 | 标记数据缺口，不推断已发生的故障。 |
| 趋势统计与单笔证据不一致 | 优先说明单笔证据及样本限制。 |

为每个检查准备可重复输入，记录实际观察。验收时对照产物、状态或数值，不只阅读一段看似合理的解释；尚未验证的项目保留为待验收，不能按通过统计。

### 一组可直接核对的验收样例

以下为合成验收样例，展示预期行为，不是生产环境的实测结果。可先实现这一最小样例，再加入前面的故障条件。

```json
{
  "input": {
    "segments": [
      {
        "hours": 1,
        "rate": 2
      },
      {
        "hours": 0.5,
        "rate": 4
      }
    ],
    "billed": 5
  },
  "expected": {
    "calculated": 4,
    "difference": 1,
    "cause": "requires investigation"
  }
}
```

复算可证明账单与本例费率之间存在差额，却不能直接判定是设备故障或计费系统错误；还需要核查服务费等口径。
