## 场景与成果

**案例文档** · 无需访问原内网入口或演示视频，可在本页了解场景与复用方法。

把设计问答、规范检查和用户采纳反馈转成知识提案，经评测与审核后更新知识版本。

本篇根据 showcase 资料整理，原案例贡献者：Qoder Agents 团队。内容介绍材料中的方案，不将其等同于已验证的生产部署或量化收益。

## 实现思路

案例描述八步链路：任务进入、知识服务、交互执行、结果反馈、缺口识别、提案生成、评测审核和灰度发布。知识消费产生的新信号进入受控更新流程。

### 实践演练：从任务到验收

用测试设计规范检查一个按钮组件，记录设计师采纳或修改的反馈，再生成一份知识修订提案。

以下是可复用的实现与验收建议，不代表演示站已公开这些后端能力，也不表示这些检查已经执行通过。演练使用合成或获授权输入；JSON 是应用侧记录示意，不是 QCA API 请求。

### 分步实现与交付物

#### 1. 执行检查

按当前规范版本定位问题，附组件、规则和观察证据。

#### 2. 收集反馈

记录建议被采纳、修改或拒绝及其原因，将反馈关联到原任务。

#### 3. 生成提案

描述知识缺口、拟修改内容、适用范围和影响样本，不直接发布规则。

#### 4. 评测发布

用参考设计回放新旧规则，经审核后小范围启用，保留回滚版本。

### 输入输出记录示例

```json
{
  "proposal_id": "design-rule-demo",
  "base_version": "v1",
  "rule": "button-spacing",
  "evidence": [
    "feedback-01"
  ],
  "state": "review-required",
  "rollout": "test-project"
}
```

将这份记录与产物或报告一起保存，用来回答“这份结果来自哪个输入、哪个版本”。凭证不写入记录。输入变化后应重新判断旧结果是否适用，不能静默复用。

## 复用建议
从一种规范检查开始，记录修改原因与证据；将提案和已发布规则分开，通过参考样本评测后再发布，并保留回滚版本。

### 关键取舍

采纳率不是知识正确性的唯一指标。某条建议被接受可能只是局部偏好；知识升级还需要适用范围、反例和专家判断。

### 故障与验收检查

| 检查条件 | 预期结果 |
|---|---|
| 用户偏好与全局规范冲突 | 保留局部偏好，不自动改全局规则。 |
| 新规则修复一例却破坏旧例 | 评测阻止发布并报告回归。 |
| 上线后采纳质量下降 | 回滚版本并保留分析记录。 |

为每个检查准备可重复输入，记录实际观察。验收时对照产物、状态或数值，不只阅读一段看似合理的解释；尚未验证的项目保留为待验收，不能按通过统计。

### 一组可直接核对的验收样例

以下为合成验收样例，展示预期行为，不是生产环境的实测结果。可先实现这一最小样例，再加入前面的故障条件。

```json
{
  "input": {
    "feedback": "prefer tighter spacing",
    "scope": "one campaign"
  },
  "expected": {
    "proposal_scope": "one campaign",
    "global_rule_changed": false
  }
}
```

一次项目偏好不构成修改全局规范的依据。提案需要说明适用范围，后续参考样本与专家审核才能决定是否推广。
