## 场景与成果

设计问答与规范检查每天都在消费知识，也会产生修订、拒绝和专家判断。这个案例把这些反馈带回知识维护流程，让后续服务能够使用经审核的新版本。

把设计问答、规范检查和用户采纳反馈转成知识提案，经评测与审核后更新知识版本。

本文根据Qoder Agents 团队提供的 showcase 资料整理。流程图与分工表用于解释案例中的方法；后面的具体示例是复用建议，不作为生产运行的实测结论。

## 实现思路

### 一次任务如何流经产品

案例描述八步链路：任务进入、知识服务、交互执行、结果反馈、缺口识别、提案生成、评测审核和灰度发布。知识消费产生的新信号进入受控更新流程。

```mermaid
flowchart LR
  N0["执行检查"] --> N1
  N1["收集反馈"] --> N2
  N2["生成提案"] --> N3
  N3["评测发布"]
```

每个环节都需要把自己的输入与结果交给下一步。后续步骤据此继续工作，用户也能沿着这条链查看结果从哪里产生、在哪一步需要确认。

### 角色分工与权威事实

| 组成部分 | 在案例中的职责 |
|---|---|
| QCA Agent | 服务执行与反馈提炼 |
| 专家 | 高影响变更审核 |
| 知识库 | 版本、发布和回滚 |

采纳率不是知识正确性的唯一指标。某条建议被接受可能只是局部偏好；知识升级还需要适用范围、反例和专家判断。

### 沿着一个具体任务展开

用测试设计规范检查一个按钮组件，记录设计师采纳或修改的反馈，再生成一份知识修订提案。

1. **执行检查**：按当前规范版本定位问题，附组件、规则和观察证据。
2. **收集反馈**：记录建议被采纳、修改或拒绝及其原因，将反馈关联到原任务。
3. **生成提案**：描述知识缺口、拟修改内容、适用范围和影响样本，不直接发布规则。
4. **评测发布**：用参考设计回放新旧规则，经审核后小范围启用，保留回滚版本。

这条流程的交付物需要保留过程中使用的依据。某一步缺少数据或执行失败时，应让状态继续可见，避免后续环节把它当作已经完成的结果。

### 让结果可以被核对

下面用一组合成数据说明预期交付。它是应用侧的说明样例，不是 QCA API 请求，也不是生产记录。

```json
{
  "input": {
    "feedback": "prefer tighter spacing",
    "scope": "one campaign"
  },
  "expected": {
    "proposal_scope": "one campaign",
    "global_rule_changed": false
  }
}
```

一次项目偏好不构成修改全局规范的依据。提案需要说明适用范围，后续参考样本与专家审核才能决定是否推广。

### 实际操作：从第一条请求开始

下面是一条可用于测试环境的复现任务，用来走通应用流程；不代表原产品未公开的内部实现。

> 检查测试按钮的间距，注明采用的规范版本。把设计师反馈整理为局部知识提案，列出适用范围、支持样例、反例和评审项，先不改全局规范。

先保留原建议和设计师修改后的结果，才能解释提案从何而来。“这次活动希望更紧凑”只能支持活动范围内的偏好。用常规页面和活动页面分别回放提案，确认局部改善没有影响其他场景，再由规范维护者决定是否扩大范围。

### 读懂结果，再试一次反例

第一轮跑通后，只改变一个条件：**用户偏好与全局规范冲突**。此时应当看到的行为是：保留局部偏好，不自动改全局规则。 将前后两次结果并排保留，核对是判断发生了合理变化，还是某一步没有输出。



## 复用建议

落地时可以先复现上面的一个任务，用已知输入核对交付结果，再补齐下面这些失败或歧义场景。通过后再扩大任务范围。

| 失败或歧义场景 | 需要保留的行为 |
|---|---|
| 用户偏好与全局规范冲突 | 保留局部偏好，不自动改全局规则。 |
| 新规则修复一例却破坏旧例 | 评测阻止发布并报告回归。 |
| 上线后采纳质量下降 | 回滚版本并保留分析记录。 |
